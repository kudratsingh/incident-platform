# Postmortem 0001 — v0.4.1 schema drift caused every DLQ tool to 500

**Status:** Backfilled from code comments · **Written:** 2026 Q3 · **Owner:** Platform

## Impact

Every MCP DLQ tool (`list_dlq_messages`, `get_dlq_message`, `replay_dlq_messages`) returned HTTP 500 for the duration of the incident. The agent's incident-response loop was fully blocked — it had no way to inspect or replay dead-lettered jobs. Read-only telemetry tools (`get_consumer_lag`, health probes) kept working, so the outage looked partial rather than total from a naive dashboard.

Duration: **several hours** before an operator spotted the pattern in the structured logs.

## Timeline

Rough — reconstructed from git history and code comments, not from live incident notes.

- **v0.4.1 release ships** with a migration that adds `jobs.remediation_hint` (new column consumed by the DLQ tool responses).
- **Deploy step runs `docker compose restart`** on the affected environment instead of `docker compose up` or an explicit `alembic upgrade head`. `restart` re-runs the container's `command:` — for the app container that meant uvicorn — but does *not* re-invoke the separate migrate one-shot. The migration never runs.
- **App boots green.** The FastAPI lifespan reports "startup" cleanly. No warning that `alembic_version` is behind `head`.
- **First DLQ tool call arrives.** The SQL query references `jobs.remediation_hint`; Postgres raises `column "remediation_hint" does not exist`; the handler wraps it as an internal 500. The response has a `request_id` but no hint that the underlying cause is schema drift.
- **Agent retries.** Every retry hits the same path, same error.
- **Operator eventually greps the structured logs**, sees the `column "remediation_hint" does not exist` string in the WARN stream, runs `alembic upgrade head` manually. DLQ tools recover on the next call.

## Root cause

Two things had to be true:

1. **The deploy step was `docker compose restart`, not `docker compose up`.** `restart` only recycles the running containers — the one-shot migrate step lives in a separate compose service (`migrate:`) that only runs on `up`. This distinction wasn't documented in the runbook of the day, and the operator followed muscle memory.
2. **The app booted successfully with a schema behind its code.** SQLAlchemy doesn't validate the schema on startup; it discovers the mismatch on the first query that touches the missing column. If the missing column is on a hot path, the platform looks fine until traffic hits that path.

The compose-restart mistake was the trigger. The "silent boot on stale schema" was the amplifier — it turned a bad ops step into a several-hour incident that presented as intermittent DLQ tool failures.

## Detection gap

- **No startup check** compared `alembic_version` against the code's `head` revision. The app had every reason to know its schema was stale at boot; it did not check.
- **No alarm on 500 rate spike** for the MCP surface specifically. The existing `alb-5xx` alarm aggregates across all routes and had a threshold high enough to absorb this without paging.
- **No structured log field** on the exception path carried the SQLAlchemy error message in a queryable shape; the operator had to grep. A "schema-mismatch" heuristic in the exception middleware could have surfaced this in one dashboard glance.

## Fix

Landed as part of the same release cycle:

- `backend/app/core/migration_check.py` — `assert_migrations_current(session_factory)` compares the DB's `alembic_version.version_num` against the code's `alembic.script.ScriptDirectory.get_current_head()`. Mismatch raises before the lifespan yields.
- `backend/app/main.py` — API lifespan calls `assert_migrations_current(...)` after the container-startup log line and before the worker loop starts.
- `backend/app/mcp/standalone.py` — MCP lifespan does the same; the MCP process doesn't run workers but hits the DB on every tool call, so a schema behind the code is fatal.
- Both fail loud — uvicorn crashes on boot with a `RuntimeError` naming the head/DB revisions instead of silently accepting traffic against a stale schema. A crashed container triggers the existing "ECS tasks low" CloudWatch alarm within one health-check cycle.

## Prevention rule adopted

**The app must not accept a single request against a schema behind its code's `head` revision.** Enforcement is `assert_migrations_current` in every lifespan that hits the DB. A future service that adds a lifespan and skips this check is a regression; the review-time signal is that no new lifespan should exist without the assertion.

The follow-on procedural rule: **`docker compose restart` is banned for platform deploys**; the runbook specifies `docker compose up -d` (which honors the `depends_on: migrate` chain) or an explicit `alembic upgrade head` step before starting the app service. Documented in `docs/runbook.md` (commander repo).
